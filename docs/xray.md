# Xray in Củ Chi

Register a dedicated Ubuntu VPS with the existing SSH form, then choose **Развернуть Xray** on its server card. Open TCP/443 at the provider. The worker installs Docker if required and runs the official Xray-core 26.11.9 image pinned by digest. A clean server can run Xray alone. Each server uses its own X25519 key pair and short ID. During initial deployment the worker tests candidate TLS destinations from the VPS for certificate validity, TLS 1.3 and ALPN h2. It saves a domain after a real VLESS/Vision + REALITY connection carries an HTTPS request. Subsequent reconciliations reuse the saved domain. Release validation runs this installer on a disposable Ubuntu CI runner.

In **Устройства**, issue Xray for a device, wait for the server to confirm application, then select **Подключить Xray**. Import the subscription URL or its QR in a client compatible with the deployed REALITY version. Individual VLESS links are also available. Each enrolled device gets a distinct credential per server. Adding another Xray node automatically provisions existing enrolled devices. Refresh the subscription in the client to fetch its updated list. Hiding a server removes it from refreshed lists. Revoking device access immediately invalidates its subscription and queues server-side removal. An unavailable server keeps revocation pending until it confirms removal. Device deletion waits for this confirmation.

NAS migration 015 is additive. The API uses Synology roles, ownership checks and CSRF. SSH credentials and pins use the existing server inventory. The database/master-key backup covers Xray identities and device subscriptions. Subscription URLs and QR codes grant access: keep them private, including reverse-proxy access logs. The Xray container exits directly via the VPS. AWG/WARP, default-server reminders, Keenetic uplinks and AWG statistics retain their own settings. The server card shows the last application result. A deployment probe proves VPS-side forwarding; reachability from a particular ISP needs a connection from that network.

Applying an updated device list briefly restarts Xray connections on that VPS. A failed candidate is removed and the worker attempts to restore the previous runtime. The worker retries failed deployment after three minutes. To roll back the NAS binary, first revoke Xray grants you intend to remove and verify all servers have applied them. An older NAS version cannot manage deployed Xray containers.

When a new server first passes the deployment probe and is published, Củ Chi adds an informational announcement to the inbox of every existing authorized user, including people who only use AWG. Browser push uses the profile-reminder preference and opens Devices. Choose **Развернуть без публикации** to run the probe privately, then **Добавить в подписки** to release it. Retries, client changes and hiding/showing an announced server do not create another announcement. Servers already published and applied before migration 016 are treated as previously available.

## Android client compatibility

NekoBox for Android 1.4.2 removes the hybrid TLS key share required by Xray-core 26.11.9. In a same-route comparison using a single subscription entry, the NekoBox core reported `reality verification failed` while the official Xray client carried HTTPS to the VPS exit. Refreshing the subscription does not change the client handshake. The [NekoBox implementation](https://github.com/MatsuriDayo/sing-box/blob/aed32ee3066cdbc7d471e3e0415c5134088962df/common/tls/reality_client.go#L118-L130) and [REALITY server change](https://github.com/XTLS/REALITY/commit/8cdf7bf9c7f0) describe the mismatch.

A desktop test over an existing VPN does not verify the phone's ordinary path. Stop any failing system VPN before a standalone test. Check ordinary Android application traffic and the observed exit IP as well as the client's built-in latency test.

On the tested Android Wi-Fi path, the official v2rayNG 2.4.0 prerelease with core 26.11.9 retained the subscription after an in-place update from 2.3.15. With its Android VPN active, two batches of eight HTTPS requests completed and two exit-IP services in Chrome showed the expected VPS address. These results apply to the tested phone, network and release.
