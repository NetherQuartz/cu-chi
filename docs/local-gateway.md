# Домашний шлюз для Keenetic

Keenetic → обычный WireGuard по LAN → отдельная Ubuntu VM → AmneziaWG 3.1 → VPS.

Панель на NAS управляет VM по SSH, как VPS. Она не получает Docker socket, TUN или сетевые привилегии NAS. У шлюза отдельное устройство и отдельный профиль на VPS; статистика этого устройства суммирует трафик всех клиентов за Keenetic. Локальные ключи WG сохраняются в зашифрованной базе панели независимо от профилей VPS и включены в существующие резервные копии базы/master key.

## Подготовка VM

- Ubuntu Server 24.04 / 26.04 LTS amd64 без графического рабочего стола. Начальная конфигурация: 2 vCPU, 2 ГБ RAM, 25 ГБ диска. Это запас для ОС/Docker/обновлений, не гарантия пропускной способности: её измеряют на конкретном CPU. [Ubuntu Server requirements](https://ubuntu.com/server/docs/system-requirements/).
- Один сетевой интерфейс в домашней сети через виртуальный коммутатор VMM. Закрепите IPv4 VM в DHCP Keenetic. Не используйте для LAN диапазоны 10.66.0.0/16 (AWG) и 10.77.0.0/24 (локальный WG).
- Включите OpenSSH Server **в VM**, а не на NAS. Используйте отдельную выделенную VM, root или администратора с sudo без пароля. Обычный Ubuntu-пользователь с паролем SSH не получает автоматически sudo без пароля. Настройте это в консоли VM перед подключением; панель не меняет sudoers/sshd.
- У VM должен быть прямой интернет через Keenetic для Docker/обновлений и внешнего AWG транспорта. NAS и VM не включайте в клиентскую VPN-политику Keenetic, иначе возникнет петля маршрутизации.
- Нужны TUN, модуль ядра WireGuard и неактивный UFW; применяется тот же ограниченный профиль целевой ОС, что для VPS. Деплой проверяет LAN-адрес VM и загружает модуль WireGuard. Произвольные существующие firewall/сетевые настройки не поддерживаются первым вариантом.

## Настройка из панели

1. Откройте **Шлюзы → Добавить шлюз**. Введите IP VM, IP Keenetic, SSH-пользователя и пароль / сохранённый ключ / отдельный ключ. Сохранённый ключ создаётся в разделе «Серверы»; его публичную часть заранее добавьте пользователю VM. TOFU запоминает первый ключ хоста; последующие подключения строго проверяют его.
2. При маршрутизации без NAT со стороны Keenetic укажите сети клиентов, например `192.168.50.0/24`. С NAT достаточно WG-адреса роутера, который уже включён. Ключи локального WG и сетевые параметры фиксируются при регистрации. Редактирование/ротация LAN-идентичности пока не реализованы.
3. **Проверить SSH** проверяет доступ/базовую совместимость. **Выпустить профиль VPS** создаёт отдельный профиль на основном VPS. Дождитесь готовности.
4. **Развернуть на VM** ставит долговечное задание. Панель устанавливает Docker, загружает закреплённый digest образа из GHCR, передаёт конфиги в root-only каталог, запускает контейнер и проверяет DNS/HTTPS через AWG. Автоматические повторы ограничены тремя попытками; повторное применение использует те же ключи. Конфиги не попадают в логи или аргументы SSH-команды.
5. Скачайте **Профиль для Keenetic** и импортируйте его в обычный WireGuard. Один такой профиль — один роутер. Не копируйте его на независимо подключающиеся устройства.
6. На Keenetic включите использование этого подключения для интернета и создайте **отдельную политику только с WG**, без ISP/WAN в качестве резервного подключения. Привяжите выбранные устройства к этой политике. Профиль задаёт DNS `1.1.1.1, 1.0.0.1`; убедитесь, что DNS выбранных клиентов действительно направляется через WG, включая DNS-запросы самого резолвера Keenetic. Не оставляйте для этой политики DNS провайдера как резервный.
7. Для первого варианта отключите IPv6 в VPN-сегменте/на выбранных клиентах: локальный профиль WG обслуживает IPv4. Блокировка IPv6 внутри VM **не может** запретить роутеру отправлять IPv6 напрямую по другой сети.

[Официальная настройка интернета через WireGuard на Keenetic](https://help.keenetic.com/hc/en-us/articles/360010551419-internet-access-through-a-wireguard-vpn-tunnel/35336-site-details-page.html), [политики подключений Keenetic](https://support.keenetic.com/hero/kn-1013/en/17892-connection-policies.html).

## Блокировка при отказе и независимость

В контейнере FORWARD изначально DROP для IPv4/IPv6. Разрешено только wg0 → awg0 и установленный обратный поток. Трафик с wg0 использует отдельную таблицу маршрутов с постоянным unreachable default; исчезновение AWG не приводит к переключению на eth0. Маршрут по умолчанию контейнера/VM остаётся прямым для транспорта туннеля и управления. NAT выполняется только на выходе AWG. Обратная таблица возвращает маршрутизируемые LAN-адреса через WG без перехвата локального адреса Keenetic для транспортных пакетов. Профиль разбирается по ограниченному диалекту, PostUp/PreDown и любые shell-хуки не выполняются.

Развёртывание проверяет выход из VM, но не настройку политики роутера. Для полного fail-closed нужны обе части: контейнерная блокировка и отсутствие прямого резерва на Keenetic. При недоступности самой VM роутер также должен оставлять выбранных клиентов без интернета.

Контейнер продолжает работать при остановке панели/БД. Перезапуск VM восстанавливает последнюю конфигурацию через Docker restart policy. Docker healthcheck раз в минуту проверяет DNS/HTTPS через AWG; статус unhealthy не включает прямой выход и не перезапускает контейнер автоматически. В панели показывается **время проверки при последнем применении**, а не выдуманный текущий статус шлюза. После трёх неудачных попыток развёртывания администраторы получают уведомление в кабинете и Web Push с учётом настроек категории ошибок управления. Повторное задание прекращает отправку устаревшего предупреждения. Периодический сбор состояния VM и отдельные gateway-инциденты пока не реализованы.

## Замена VPS и восстановление

Выберите новый основной VPS. В разделе «Шлюзы» обновите профиль VPS, дождитесь установки на сервере, затем нажмите **Применить профиль на VM**. Перевыпуск отзывает прежний профиль: до применения нового будет перерыв VPN. На Keenetic ничего переимпортировать не нужно — локальные WG-ключи и адрес VM прежние.

Если VM недоступна, задание остаётся видимой ошибкой; старый профиль нельзя считать обновлённым. При изменении профиля во время задания результат не отмечается как актуальный. Пин SSH не заменяется автоматически. База хранит разные идентификаторы текущего и применённого профилей.

Удаление связанного устройства заблокировано, пока оно является управляемым шлюзом. Автоматическое удаление/деинсталляция шлюза и смена его LAN-параметров — следующий отдельный этап; контейнер можно остановить в VM, сохранив LAN-идентичность в базе. Не удаляйте шлюзовые ключи из резервной копии вместе с заменяемым VPS.

## Образы и проверка

CI собирает именованный target `gateway` в `deploy/awg/Dockerfile`: тот же закреплённый AWG 3.1 + обычный `wireguard-tools-wg` для ядра Ubuntu. Публикует `ghcr.io/netherquartz/cu-chi-gateway:sha-<commit>` для amd64 только после пакетных тестов. Digest встраивается в образ панели, так что на VM не нужны GitHub-токены или локальная сборка. Обновление панели само не перезапускает шлюз; новый образ применяется следующим заданием.

`deploy/gateway/compose.yaml` — дополнительный вариант для ручной установки в Linux VM, не изменение NAS Compose. Основной пользовательский путь — раздел «Шлюзы». Для ручного варианта локальную идентичность создаёт `docker compose run --rm -v ./config:/config:rw gateway init`; существующую идентичность команда не перезаписывает. Профиль из портала кладётся в `config/uplink.conf` с правами 600; `config/lan` сохраняется при замене VPS.

Пакетные тесты запускают настоящий kernel WG → userspace AWG, проверяют крупную передачу с NAT и без NAT на клиенте, DNS/HTTPS, обрыв peer, удаление AWG-интерфейса, восстановление и перевыпуск uplink с неизменной WG-идентичностью. Реальная VM/VMM, импорт на Keenetic, DNS/IPv6 и отсутствие WAN fallback требуют отдельной приёмки на домашней сети.
